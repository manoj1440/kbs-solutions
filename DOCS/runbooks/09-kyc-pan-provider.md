# Identity (Aadhaar via DigiLocker) and PAN checks — Cashfree Secure ID (ADR-009)

How to replace the two mock checks with the real provider the owner chose, **Cashfree Secure ID** (Cashfree's
"Verification APIs"):

| Check | Port | Env switch | Adapter |
|---|---|---|---|
| Advisor identity at onboarding (REQ-10) | `KycProvider` | `KYC_PROVIDER=cashfree` | `apps/api/src/providers/adapters/cashfree-digilocker-kyc.adapter.ts` |
| Customer PAN at lead creation (REQ-11) | `PanVerificationProvider` | `PAN_PROVIDER=cashfree` | `apps/api/src/providers/adapters/cashfree-pan.adapter.ts` |

Shared code: `cashfree-verification.client.ts` (HTTP, headers, 2FA signature), `name-match.ts` (name rule); boot
validation in `apps/api/src/config/env.ts`.

**Status: code complete and unit-tested against a stubbed HTTP client. No request has ever been sent to Cashfree** — there
was no Cashfree account when it was written. Everything below about Cashfree's behaviour comes from its public
documentation (read 2026-11-11, listed at the end). Treat step 4 as the real test and read "Not verified" first.

## What the code does

Every call: one attempt, no automatic retry, 10 s timeout, headers `x-client-id`, `x-client-secret`,
`accept: application/json` (plus `content-type: application/json` on POST, and `x-cf-signature` when a public key is
configured — see 2FA below). Base URL by `CASHFREE_VERIFICATION_ENV`:

| `CASHFREE_VERIFICATION_ENV` | Base URL |
|---|---|
| `sandbox` | `https://sandbox.cashfree.com/verification` |
| `production` | `https://api.cashfree.com/verification` |

### PAN (`PAN_PROVIDER=cashfree`)
```
POST <base>/pan
x-api-version: <CASHFREE_VERIFICATION_API_VERSION, default 2024-08-01>

{ "pan": "<PAN>", "name": "<customer name>" }
```
The name is reduced to the characters Cashfree allows (letters, digits, space, `.`, `-`, `/`, `&`). A PAN that is not
PAN-shaped is answered `FAILED` without calling Cashfree.

| Cashfree answer | KBS result |
|---|---|
| 200, `valid: true` (and `pan_status` absent or `VALID`), name matches | `VERIFIED` |
| 200, `valid: true`, name does not match | `MISMATCH` (lead creation is blocked) |
| 200, `valid: false`, or `pan_status` is `INVALID` / `DELETED` / `DEACTIVATED`; 400 with a `pan_…` code | `FAILED` |
| timeout, network error, 401, 403, 422 (wallet empty), 429, 5xx, any other 4xx, a body that is not the documented shape, valid PAN but nothing to compare the name with | `UNAVAILABLE` — never `FAILED`: an outage must not look like a bad PAN |

Name match, in this order:
1. Cashfree's own `name_match_result`, when the account has the (separately activated, chargeable) name-match feature:
   `DIRECT_MATCH` and `GOOD_PARTIAL_MATCH` count as a match; `MODERATE_PARTIAL_MATCH`, `POOR_PARTIAL_MATCH`, `NO_MATCH`
   do not. No score threshold of our own is applied.
2. Otherwise `registered_name` is compared in memory with the rule below, then dropped. KBS does not depend on the paid feature.

`providerRef` is Cashfree's numeric `reference_id`. The registered name, the PAN and the customer name are never returned
by the adapter or logged. (The leads module keeps the PAN encrypted and its last four characters, as before.)

### Aadhaar via DigiLocker (`KYC_PROVIDER=cashfree`, method `DIGILOCKER_AADHAAR`)
The Advisor signs in on DigiLocker's own page and consents there. Nothing identity-related is typed into the KBS app.

**start**
```
POST <base>/digilocker

{ "verification_id": "kbs-<32 hex>", "document_requested": ["AADHAAR"],
  "redirect_url": "<API_PUBLIC_URL>/api/v1/onboarding/identity/return",
  "user_flow": "signup", "company_name": "KBS Solutions" }
```
`verification_id` is generated by KBS (36 characters, limit 50, no personal data) and becomes the session reference.
Cashfree's `url` (valid 10 minutes) is returned to the app as `actionUrl`. `user_flow: signup` is Cashfree's default and
works whether or not the person already has a DigiLocker account. Any failure here → the Advisor sees "The identity
verification service is unavailable right now. Please try again later."

**complete** (the Advisor taps "I have completed verification")
```
GET <base>/digilocker?verification_id=kbs-<32 hex>
GET <base>/digilocker/document/AADHAAR?verification_id=kbs-<32 hex>      (only when the first says AUTHENTICATED)
```

| Cashfree answer | KBS result (`evidenceSummary.reason`) |
|---|---|
| status `PENDING`; document call answers 202 `validation_pending` | `PENDING` — nothing recorded, the session stays open |
| status `EXPIRED`; document 400 `url_expired` | `FAILED` (`LINK_EXPIRED`) |
| status `CONSENT_DENIED` | `FAILED` (`CONSENT_DENIED`) |
| document 400 `session_expired` / `consent_not_granted` / `user_detail_mismatch` | `FAILED` (`CONSENT_SESSION_EXPIRED` / `DOCUMENT_CONSENT_NOT_GIVEN` / `PROVIDER_DETAIL_MISMATCH`) |
| document 200 with status `AADHAAR_NOT_LINKED` | `FAILED` (`DOCUMENT_NOT_LINKED`) |
| 404 `not_found_error` + `verification_id_value_invalid` | `FAILED` (`SESSION_NOT_FOUND`) |
| document 200 `SUCCESS`, name on the document ≠ profile name | `FAILED` (`NAME_MISMATCH`) |
| document 200 `SUCCESS`, no name / no usable date of birth / under 18 | `FAILED` (`NAME_NOT_READABLE` / `AGE_UNKNOWN` / `MINOR`) |
| document 200 `SUCCESS`, name matches, 18 or older | `VERIFIED` |
| no profile name passed to the adapter | `FAILED` (`PROFILE_NAME_MISSING`) — Cashfree is not called |
| timeout, network error, 401, 403, 422, 429, 5xx, any other 404 / 4xx, unknown status, non-JSON body | `UNAVAILABLE` |

A plain 404 is deliberately `UNAVAILABLE`: Cashfree answers 404 on the DigiLocker endpoints when DigiLocker has not been
activated on the account.

Fields read from Cashfree: status call — `status`, `reference_id` only (its `user_details` block is ignored). Document
call — `status`, `reference_id`, `name`, `dob`, `year_of_birth` only. Age is counted in whole years on today's date in
India; with only a year of birth it is decided only when every birthday in that year gives the same answer, otherwise
`AGE_UNKNOWN`.

The adapter keeps nothing between requests, so the onboarding service passes the profile name again at complete time as
`payload: { fullName }`.

### Name rule (`name-match.ts`)
Decided 2026-11-11 (engineering decision on the owner's instruction, for this product): the person is already
authenticated by the provider — their own DigiLocker, or the PAN record — so this is a consistency check, not the
security gate. Exact-only matching would block genuine users whose document carries a middle or father's name or an
initial, and each retry is a paid verification.

After normalising (Unicode, accents dropped, upper-case, punctuation to spaces, leading honorifics MR / MRS / MS / MISS /
DR / SHRI / SMT / SHRIMATI / KUM / KUMARI removed) two names match when any of:
- the words are the same in any order ("SHARMA RAJESH" = "Rajesh Sharma");
- they are equal once spaces are removed ("RAJESHKUMAR" = "Rajesh Kumar", "R.K. Sharma" = "RK Sharma");
- every word of the shorter name is found in the longer one — a one-letter word may stand for a word starting with that
  letter — and at least two full words agree exactly ("Rajesh Sharma" = "Rajesh Kumar Sharma"; "Rajesh K Sharma" =
  "Rajesh Kumar Sharma").

Not a match: only one full word in common ("Rajesh" vs "Rajesh Sharma"; "R Sharma" vs "Rajesh Sharma"), a word the
document does not have, spelling variants ("Mohd" vs "Mohammed"), a different word ("Rajesh" vs "Rakesh"). No similarity
score is used. On a mismatch the Advisor is told to enter the name exactly as on the Aadhaar and verify again.

Consequence to expect in support: an Advisor who entered only one name, or a name with a different spelling from the
Aadhaar, gets `NAME_MISMATCH` and is told to enter the name exactly as on the Aadhaar and verify again. A left-out
middle or father's name no longer fails.

## Data minimisation (REQ-10, REQ-21)
KBS stores for identity: the outcome (`VERIFIED` / `FAILED` / `UNAVAILABLE`), the provider name (`cashfree`), the method
(`DIGILOCKER_AADHAAR`), the provider reference (Cashfree's numeric reference id, or the KBS session id), the time, and
the summary `{ method, verifiedNameMatch, ageBand, reason? }`. For PAN: the outcome and Cashfree's reference id (next to
the encrypted PAN the leads module already keeps).

Never stored, returned or logged by these adapters: Aadhaar number (masked or not), photo, address, date of birth, year
of birth, gender, care-of, DigiLocker mobile number, the XML link, the PAN registered name, the raw responses, the client
secret, the signature, the DigiLocker URL. The Aadhaar document exists only in memory for the duration of one request.
Logs carry the KBS session id, Cashfree's reference id, the HTTP status and Cashfree's error `code` — never Cashfree's
error `message` (it can echo the caller's IP or the input).

Cashfree itself keeps the verification records in its dashboard under its own retention; that is part of the contract
with Cashfree, not something this code controls.

## 1. Outside the code — what the owner must do
1. **Cashfree merchant account** with business KYC completed, then open **Secure ID** (apps icon → Secure ID). Secure ID
   has its own API keys (client ids normally start with `CF`) — the Payment Gateway keys do not work.
2. **Activation.** PAN verification, and **DigiLocker separately**: Cashfree's FAQ says DigiLocker needs account-level
   activation in addition to Secure ID access (raise it with the account manager / support form). Until then the
   DigiLocker endpoints answer 404 and the app shows "service unavailable".
3. **Name match for PAN** (recommended): ask Cashfree to activate the "name match score" feature on PAN verification — it
   is a chargeable add-on. Without it the adapter falls back to the strict local rule on `registered_name`, which rejects
   e.g. a missing middle name.
4. **Sandbox keys first:** Secure ID dashboard → switch to Test → Developers → API Keys → Generate. Production keys need
   an OTP and come from the production dashboard.
5. **2FA — mandatory in sandbox and production, pick one** (Developers → Two-Factor Authentication, Secure ID card):
   - **Public Key** — the right choice on Render, which has no fixed outbound IP (Cashfree's own IP-whitelisting page says
     so). Generate the public key (one active key, downloadable once; the production file is password-protected, the
     password is e-mailed), make sure Public Key is the *active* method ("Switch Method"), and put the PEM text in
     `CASHFREE_VERIFICATION_PUBLIC_KEY`. The API then signs every request:
     `x-cf-signature = Base64( RSA-OAEP-SHA1( "<client id>.<unix seconds>" ) )`, fresh per request (valid 5 minutes).
   - **IP Whitelist** — only with a static public IPv4 (up to 25 single addresses, no ranges, no IPv6). Leave
     `CASHFREE_VERIFICATION_PUBLIC_KEY` empty: Cashfree says not to send the signature when IP Whitelist is active.
6. **Wallet:** Secure ID is prepaid; an empty wallet answers 422 `insufficient_balance` (the app shows "unavailable").
7. **DigiLocker redirect URL:** the documentation only requires it to be a valid `https` URL and does not mention
   registering it. If Cashfree asks, the URL is `<API_PUBLIC_URL>/api/v1/onboarding/identity/return`.
8. **Success-rate alerts** (Settings → Email Notifications → SR Alerts) for PAN and DigiLocker — optional, recommended.

Pricing: Cashfree publishes no rate card for Secure ID; it is quoted per account —
https://www.cashfree.com/contact-sales/ (see "What are the charges" in
https://www.cashfree.com/docs/help/secure-id/general-faqs).

## 2. Environment variables on the API host (names only — values live in the host's secret store)
| Variable | Required | Meaning |
|---|---|---|
| `KYC_PROVIDER` | — | `cashfree` (default `mock`) |
| `PAN_PROVIDER` | — | `cashfree` (default `mock`) |
| `CASHFREE_VERIFICATION_CLIENT_ID` | yes, if either is `cashfree` | Secure ID client id |
| `CASHFREE_VERIFICATION_CLIENT_SECRET` | yes | Secure ID client secret |
| `CASHFREE_VERIFICATION_ENV` | yes | `sandbox` or `production` — must match the keys |
| `CASHFREE_VERIFICATION_PUBLIC_KEY` | only with 2FA "Public Key" | the PEM; one line with `\n` for line breaks is accepted |
| `CASHFREE_VERIFICATION_API_VERSION` | no | `x-api-version` on the PAN call, default `2024-08-01` |
| `API_PUBLIC_URL` | yes for `KYC_PROVIDER=cashfree` | public **https** URL of the API (DigiLocker returns the Advisor to it) |

The API **refuses to start**, in every environment, when a cashfree provider is selected and: one of the three required
keys is missing; `NODE_ENV=production` with `CASHFREE_VERIFICATION_ENV` other than `production`; the public key is set but
is not a readable RSA PEM; or `KYC_PROVIDER=cashfree` with an `API_PUBLIC_URL` that is not https. Messages name the
variable, never a value.

`render.yaml` declares all of them as `sync: false` placeholders (fill in the dashboard; unset providers mean `mock`).
`scripts/release-check.mjs` fails on `mock` for either provider, checks the three keys, checks
`CASHFREE_VERIFICATION_ENV=production` for the production profile and an https `API_PUBLIC_URL`.

The two providers can be switched independently (e.g. PAN first, DigiLocker when its activation arrives).

## 3. Deploy order
Fill the `CASHFREE_VERIFICATION_*` values → set `PAN_PROVIDER` / `KYC_PROVIDER` to `cashfree` → deploy → confirm the API
started. `KYC_PROVIDER=cashfree` also needs the API build that serves `GET /api/v1/onboarding/identity/return` and the
app build that opens `actionUrl`.

## 4. First live test — sandbox (staging, `CASHFREE_VERIFICATION_ENV=sandbox`)
**PAN** (Cashfree's published sandbox values — https://www.cashfree.com/docs/api-reference/vrs/data-to-test-integration#pan):
1. Create a lead draft with PAN `ABCPV1234D` (documented "Valid", the reference page shows registered name `JOHN DOE`),
   customer name `John Doe`. Expect the PAN step to pass; API log: `[cashfree-pan] VERIFIED: … (ref <n>)`.
2. Same PAN, customer name `Someone Else` → "The PAN does not match the customer name"; log `MISMATCH`.
3. PAN `DEFPV0126D` (documented "Invalid") → "PAN could not be verified"; log `FAILED`.
4. Read the log line of step 1: `provider DIRECT_MATCH` means the name-match feature is on; `registered-name comparison`
   means it is not (see owner step 3).
5. If the log says `UNAVAILABLE: HTTP 403 ip_validation_failed` → 2FA: the host IP is not whitelisted; switch to Public Key.
   `HTTP 403 authentication_failed` → signature missing or rejected (key from the other environment, or Public Key is not
   the active method). `HTTP 401` → wrong keys. `HTTP 400 x-client-secret_value_invalid` → keys and
   `CASHFREE_VERIFICATION_ENV` are from different environments. `HTTP 422 insufficient_balance` → wallet.

**DigiLocker.** Cashfree's integration guide states that the sandbox DigiLocker flow needs a **real Aadhaar and real
DigiLocker data — there are no test values.** Use the tester's own Aadhaar, with a test Advisor whose profile name is
spelled exactly as on that Aadhaar:
1. Onboarding → identity step → the app opens DigiLocker. Log: `[cashfree-digilocker] session kbs-… created (ref <n>)`.
2. Before finishing, tap "I have completed verification" → "not finished yet"; log `PENDING`.
3. Finish on DigiLocker (OTP, PIN, Allow) within 10 minutes, return, tap again → identity verified; log `VERIFIED`.
4. Check the database row: `identityEvidenceSummary` is exactly `{ method, verifiedNameMatch, ageBand }`, and nothing in
   the row, the audit entry or the API log contains the Aadhaar number, date of birth or address.
5. Repeat once pressing **Deny** on the consent screen → failed, reason `CONSENT_DENIED`; once letting 10 minutes pass →
   `LINK_EXPIRED`; once with a deliberately different profile name → `NAME_MISMATCH`.

Then repeat one PAN and one DigiLocker run with production keys before launch.

## 5. Switch back to mock
Set `KYC_PROVIDER=mock` and/or `PAN_PROVIDER=mock` and redeploy. The `CASHFREE_VERIFICATION_*` values can stay; they are
ignored. The mock identity check completes only with payload `MOCK_OK`, so it is for development and automated tests,
not for real Advisors; `scripts/release-check.mjs` fails a production release on `mock`. Advisors already verified stay
verified; a DigiLocker session that was open at the switch must be started again.

## Not verified (no Cashfree account, no live call)
- That Cashfree accepts these exact requests for a real account, and that real responses have the documented field names
  and types. In particular `reference_id` (documented `int64`; a number or a digit string is accepted, anything else is
  treated as absent) and `valid` (must be a JSON boolean, otherwise `UNAVAILABLE`).
- The `x-cf-signature` construction: implemented from the documented text and the PHP/Java samples (RSA-OAEP, SHA-1,
  `clientId.unixSeconds`, Base64) and proven only by decrypting with a locally generated key pair. Not checked: the exact
  format of the downloaded production key file (password-protected download; the PEM must be extracted by hand).
- `x-api-version`: sent only on the PAN call, where the reference lists it (optional). Cashfree's 2FA FAQ also says to
  include it "in each request"; the DigiLocker reference pages do not list the header, so it is not sent there. If
  DigiLocker calls are rejected for a missing version, add it in `cashfree-verification.client.ts`.
- Whether `name_match_result` is returned on this account (feature activation), and whether `GOOD_PARTIAL_MATCH` is as
  safe in practice as its description ("mostly sure it is the same person"). Counting it as a match is a decision made
  here; restrict `NAME_MATCHED` in `cashfree-pan.adapter.ts` to `DIRECT_MATCH` if KBS wants exact names only.
- Whether `pan_status` is returned with `x-api-version: 2024-08-01`; when absent only `valid` decides.
- Which name the sandbox pairs with each test PAN beyond the single example on the reference page.
- DigiLocker: that requesting only `AADHAAR` is allowed on the account; what the consent screen shows for
  `company_name`; whether the redirect URL must be registered anywhere; what parameters Cashfree appends to the redirect
  (the reference says it "will contain the verification_id"); the real shape of the Aadhaar document response (the
  product page and the API reference show two different shapes — the API reference shape is implemented, and the adapter
  reads only `status`, `name`, `dob`, `year_of_birth`, `reference_id`); the `dob` format (documented `DD-MM-YYYY`;
  `YYYY-MM-DD` and `DD/MM/YYYY` are also accepted); whether the document call is billed per call; how long after
  consent the document stays fetchable.
- The status call may answer `AUTHENTICATED` with `eaadhaar: "N"` (Aadhaar not in the person's DigiLocker). The adapter
  does not read that flag; it asks for the document and maps what comes back (`AADHAAR_NOT_LINKED`, `consent_not_granted`).
- Cashfree's webhooks for DigiLocker are not used; the result is fetched only when the Advisor taps the button.
- `complete` makes two sequential calls, each with its own 10 s timeout — worst case about 20 s before "unavailable".
- Rate limits, wallet behaviour, and DigiLocker availability windows.
- Known app behaviour to be aware of (onboarding module, not changed here): after a `FAILED` result the stored provider
  reference becomes Cashfree's reference id, so the same session cannot be completed again — the Advisor starts a new
  one. For `UNAVAILABLE` the adapter returns the session id as the reference so that the same session can be retried.
